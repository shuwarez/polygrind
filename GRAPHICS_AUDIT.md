# PolyGrind — правила runtime-графики

Этот файл описывает текущее устройство и обязательный бюджет графики. Это не
хронология оптимизаций: старые размеры и промежуточные отчёты хранятся в истории
Git, а не переносятся в каждый свежий клон.

Пол (`FLOOR_TILE_DATA`) является отдельным исключением: он уже подготовлен как
бесшовный тайл и без прямого требования не переоптимизируется.

## Источники внутри HTML

Все runtime-изображения встроены в `PolyGrind.html` как PNG data URI. Основные
каталоги:

| Каталог | Содержимое |
| --- | --- |
| `HERO_SPRITE_DATA` | Четыре героя, по четыре кадра ходьбы. |
| `ENEMY_SPRITE_DATA`, `ELITE_SPRITE_DATA` | Обычные враги и варианты элиты. |
| `BOSS_SPRITE_DATA` | Уникальные листы боссов. |
| `MINION_SPRITE_DATA` | Пять видов свиты Некроманта. |
| `LOOT_SPRITE_DATA` | Опыт, золото и книги. |
| `RARE_ITEM_SPRITE_DATA` | Поддерживаемые редкие предметы, амулеты, перчатки, ботинки, кольца и реликвии. |
| `TOTEM_SPRITE_DATA` | Пять тотемов, по отдельному PNG 24×24 для каждого из четырёх рангов. |
| `PLAYER_PROJECTILE_DATA` и отдельные projectile-константы | Снаряды игрока, врагов и боссов. |
| `MAGE_ABILITY_SPRITE_DATA` | Эффекты способностей Мага. |
| `ENEMY_STATUS_ICON_DATA` | Семь элементальных состояний врага одним листом 112×16. |
| `FLOOR_PORTAL_SPRITE_DATA` | Портал завершения этажа: восемь кадров 64×64. |
| `CONSTELLATION_SPRITE_DATA` | Иконки созвездий. |
| `GRIM_GRIND_LOGO_STRIP`, `GRIM_GRIND_TORCH_STRIP` | Логотип и факелы главного меню. |

Изображение загружается один раз и переиспользуется всеми потребителями. UI не
получает отдельную копию ресурса: например, редкий предмет использует один ключ
на земле, в окне находки, HUD, инвентаре и сводке, а книга в сводке показывает
кадр того же листа, что анимируется на земле. Тотем использует один ранговый
ресурс на земле, в окне находки, HUD, инвентаре и сводках.

Если `Image` ещё недоступен, допустим лёгкий Canvas-fallback. Он не является
второй полноценной художественной версией ассета.

## Обязательный бюджет

| Тип | Бюджет исходного кадра для runtime |
| --- | ---: |
| Герой | 32×32 |
| Обычный враг | 40×40 |
| Крупный обычный враг | 48×48 |
| Элита | обычно 48×48 |
| Босс | минимальный достаточный; текущий ориентир 64×96 |
| Обычный миньон | 24×24 |
| Индикатор элементального состояния | 16×16 |
| Портал завершения этажа | 64×64 |
| Редкий предмет или книга | 24×24 |
| Тотем | 24×24 на каждый ранг |
| Снаряд или монета | 4–12 px по наибольшей стороне, если механика не требует большего телеграфа |
| Эффект области | минимальная ячейка, масштабируемая до фактического AoE |

Босс на экране должен оставаться не меньше чем в 2,5 раза выше героя. Коллизия и
экранный силуэт задаются отдельно.

Для каждого нового растра обязательны:

- обрезка до фактической альфа-области с минимальным безопасным запасом;
- удаление запечённого фона до уменьшения;
- минимальное разрешение относительно фактического экранного размера;
- индексированная PNG-палитра максимум 256 цветов, цель проекта — 16 индексов
  вместе с прозрачностью;
- жёсткая или контролируемая альфа без случайного полупрозрачного мусора;
- отсутствие пустых кадров, неиспользуемых фаз и исходников «про запас»;
- `imageSmoothingEnabled=false` для пиксельной графики;
- отдельное хранение механического радиуса, чтобы оптимизация текстуры не меняла
  баланс.

Логотип главного меню — намеренное исключение из цели в 16 индексов: центральная
вывеска хранит 63 непрозрачных цвета и прозрачность, по восемь кадров 512×144.
Это сохраняет мелкие металлические детали при крупном выводе; исходный фон всё
равно удаляется, а лист остаётся индексированной оптимизированной PNG.

Эффект, который читаемо выражается Canvas-примитивом, не получает отдельную
текстуру. Частицы остаются небольшими примитивами с общим потолком количества.

## Анимация и кадры

- Герои используют только четыре кадра ходьбы; отдельные ряды атак и призыва не
  хранятся.
- Обычные враги и свита меняют кадр по пройденному пути и замирают вместе с
  сущностью.
- Направление движения меняется горизонтальным зеркалированием. Спрайт не
  вращается, если вращение не является частью конкретного снаряда.
- Одинаковые снаряды используют общий таймер кадра, а не отдельный таймер на
  каждый экземпляр.
- Портал листает восемь кадров слева направо по 100 мс, зацикливается и остаётся
  привязан нижним центром; коллизия перехода хранится отдельно в `G.portal.r`.
- UI показывает стабильный кадр листа, если анимация не добавляет полезной
  информации.

## Повторяемая упаковка

`optimize_graphics.py` является единственным поддерживаемым путём массовой
подготовки и установки встроенных PNG. Скрипт обязан:

1. Проверять входные размеры, кадры и ожидаемые имена.
2. Стабильно обрезать и масштабировать исходники.
3. Писать воспроизводимые результаты в локальную `outputs/`.
4. При установке менять только целевой каталог data URI.
5. Проверять уникальность HTML-якоря и завершаться ошибкой при нуле или нескольких
   совпадениях.
6. Никогда не менять `FLOOR_TILE_DATA` как побочный эффект.

Поддерживаемые семейства режимов можно посмотреть без копирования списка в
документацию:

```powershell
$env:PYTHONUTF8=1
python optimize_graphics.py --help
```

Сюда входят сборка/установка героев, обычных врагов, элиты, боссов, свиты,
снарядов, добычи, редких предметов, амулетов, перчаток, ботинок, колец, реликвий,
тотемов,
индикаторов состояний, портала завершения этажа, эффектов Мага, созвездий и
вывески меню.

`outputs/` и исходные многомегапиксельные изображения не являются runtime и не
публикуются. В `PolyGrind.html` устанавливаются только окончательные компактные
листы.

## Проверка после изменений

Минимальный набор выбирается по затронутому ресурсу:

```powershell
node herospriteunit.js
node spriteunit.js
node bossunit.js
node locunit.js
node run-all.js
```

Дополнительно обязательна визуальная проверка в браузере:

- фон действительно прозрачный;
- кадр не обрезан и не прыгает относительно опоры;
- nearest-neighbor масштаб выглядит ожидаемо;
- модель не вращается или не зеркалится ошибочно;
- UI показывает правильный ключ и кадр;
- механический радиус и баланс не изменились.

## Что не хранится в документации

Сравнения «до/после», размеры присланных исходников, даты отдельных оптимизаций и
одноразовые замеры не являются постоянной документацией. При необходимости они
фиксируются в сообщении коммита, задаче или локальном snapshot и остаются
доступны через историю Git.
